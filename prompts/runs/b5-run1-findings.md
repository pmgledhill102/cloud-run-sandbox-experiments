# sandbox-bridge egress tunnel — security test results (b5)

Date 2026-11-07, project `<sandbox-project>`, region `europe-west1`. The harness blocked writing `FINDINGS.md` (report files aren't allowed), so the full findings are inline below. Scripts, logs and `cleanup.sh` are in a scratch directory.

## Approach
Proxy/bridge logic (X3–X6, X9, X10) was tested against the **identical** Go binaries built locally (fast, free, same code). Cloud-Run-specific attacks (X1, X2, X7, X8) ran as real Cloud Run sandbox executions from an image built via Cloud Build. I kept the target's proxy/bridge and the `sandbox do` flags byte-identical; the launcher was extended only with two env-driven control knobs (`EGRESS=1` to add `--allow-egress`, `PLANT=1` to plant host marker files) for controls C and the X7 markers.

Docs read (2026-11-07): Cloud Run sandbox CLI reference (https://docs.cloud.google.com/run/docs/reference/sandbox-cli) and Code execution in Cloud Run (https://docs.cloud.google.com/run/docs/code-execution). Load-bearing facts: "all outbound traffic from the sandbox is blocked" by default; `--rootfs` default `/` = the executing container's root, read-only, and "sandboxes can read host container files"; docs warn against secrets in `--env`.

## Code vs comment disagreements (P3)
- **D1** `proxy/main.go` header says a destination is allowed only when "**every** address it resolves to is public." The code (`dial`) *skips* non-public addresses and dials the first public one — it allows if **at least one** address is public. Observed behaviour (X4) matches the **code**. The security-relevant half (a non-public address is never dialled) does hold, so this is a doc overstatement, not a hole.
- **D2** Both the proxy header and `launcher.sh` say "socat inside the sandbox exposes it as 127.0.0.1:3128." The actual mechanism is `stdio-bridge inside -forward` over yamux; socat is installed but unused. Doc-only; behaviour matches code.

## Results per attack (P1/P2/P4 — every attack has result, evidence, control, label)

**X1 Direct egress — BLOCKED (no finding).** In-sandbox `probe dial 140.82.121.6:443`, `[2606:50c0:8000::153]:443`, and by-name all fail "network is unreachable"; DNS to 169.254.169.254:53 unreachable. **Control C** (same image, `--allow-egress` added): direct-get 200, dial IPv4 ok, resolve ok — direct egress works *when egress is allowed*, so the target's omission of `--allow-egress` is what enforces X1. Label: defense holds.

**X2 Metadata — BLOCKED (no finding).** From sandbox: `probe dial 169.254.169.254:80` → network unreachable; via proxy `probe proxy-get http://169.254.169.254/` → 403 (IP literal), `http://metadata.google.internal/` → 403 (not allowlisted). **Control B** (host container): `probe dial 169.254.169.254:80` → **connected** (host reaches metadata). **Control C** (sandbox+egress): metadata dial → i/o **timeout** even with egress (Cloud Run blocks the metadata IP regardless). Note: `curl http://169.254.169.254/...` *without* `-x` returned 403 not a network error, because curl honors the injected `http_proxy` env — those were proxy denials, not direct hits; the raw `probe dial` is the clean control. Label: defense holds.

**X3 Proxy rule parsing — BLOCKED (no finding).** Denied: IPv4 literal, bracketed IPv6, IPv4-mapped IPv6 `::ffff:127.0.0.1`, `[::1]`, decimal/hex/octal IP (treated as hostnames → not-allowlisted), ports 22/8443, `http://api.github.com@example.com/` (uses `URL.Hostname()`=example.com), fragment trick. Allowed→same allowlisted host: UPPERCASE, trailing dot. Controls (permitted forms) allowed. Evidence in `proxy-x3.log`, `proxy-x6b.log`.

**X4 DNS — no private/metadata reach (limitation, low).** `priv.test`(10.1.2.3) and `meta.test`(169.254.169.254) → denied "resolves to non-public address". `both.test`(1.1.1.1+10.0.0.5) → allowed, **dialled 1.1.1.1 only**; `privfirst.test`(10.9.9.9 then 1.0.0.1) → allowed, **dialled 1.0.0.1** (private skipped in either order). Control: public-only `api.github.com` allowed. Evidence `proxy-x4.log`. Ties to D1.

**X5 Rebinding — structurally closed (no finding).** `dial()` does one `LookupIPAddr` and dials `JoinHostPort(a.IP.String(),port)` from that slice — the `upstream` in every allow log is an IP literal, proving check-IP == dial-IP (no re-resolution between check and dial). Flipping `both.test` to private-only (after Go's hosts cache expired) → next request **denied** (`proxy-x5b.log`), showing no cached allow. The flip test would have caught a proxy that re-resolved by name at dial time; it didn't fire. Label: defense holds, test proven able to fire.

**X6 Domain/SNI fronting — BYPASS (limitation by design; medium-high).** Through a CONNECT to allowlisted `api.github.com:443`, inner SNI+Host of **github.com** returned **HTTP 200** (github.com homepage) and **raw.githubusercontent.com** returned 301 — both NON-allowlisted, both reached. The proxy log only ever recorded `api.github.com`. Control: direct CONNECT to github.com → **403 deny**. Evidence `proxy-x6b.log`. The proxy decides on the CONNECT host line only and is blind to the TLS ClientHello/Host; any origin co-hosted on the same CDN edge as an allowlisted host (GitHub/Fastly here; Cloudflare via speed.cloudflare.com) is reachable — a usable exfil/C2 path via an attacker-controllable co-fronted tenant.

**X7 Host-container files readable from inside — EXPOSURE (high as a property).** The sandbox runs as **uid 0** with default `rootfs=/`, so it read every host file tried, including **root-owned mode-0600** ones: `/root/b5-baked-0600`, `/root/b5-marker-0600`, `/run/b5-secret`, plus `/etc/egress-proxy/allowlist.txt`, `/opt/target/launcher.sh`, the Go binaries. Nuances: host `/tmp` is **shadowed** by the sandbox's own tmpfs (host `/tmp/b5-marker-tmp` not visible); `/bridge/proxy.sock` is **visible but connect is refused** (ECONNREFUSED) — the stdio tunnel is genuinely the only route; `/proc/1/cmdline` inside shows only the sandbox entrypoint, not host args. **Control B** (host): all markers incl. `/tmp` readable and the socket connectable, as expected. In *this* target nothing secret lives in the container, so nothing leaks today — but the sandbox is **not filesystem-isolated by default**; any secret the host writes to its FS (outside /tmp) before launch is exposed to untrusted code. `--rootfs <minimal image>` would change this.

**X8 Logged command lines / env — EXPOSURE (medium).** Two sinks, both proven with the harmless marker `canary-b5-x8`: (1) data-plane Cloud Run logs carry the full in-sandbox command line `sandbox do --write --env HTTPS_PROXY=... --env ... -- ...` via the platform `[start]`/`[end]` lifecycle lines; (2) the per-execution `--env`/args overrides (`crun.py` `RUN_ENV`) appear **2× in the Admin Activity audit log** (`Jobs.RunJob` request). Readers: the 3 project owners and anyone with `roles/logging.viewer`; Admin Activity is non-disableable and retained ~400 days. The target passes only proxy URLs via `--env` (harmless), but `crun.py`'s `RUN_ENV` path means any secret handed to it would persist in audit logs.

**X9 Tunnel service confusion / malformed frames — contained (limitation, low).** A malicious yamux client (modelling the inside end) against `stdio-bridge host -target proxy=...`: configured name `proxy\n`+HTTP reached api.github.com (the **only** dial in `proxy-x9.log`); `build`, `zzz`, no-newline, 1 MiB name, `../../bridge/proxy.sock`, and 64 unknown streams were all refused with no dial and no crash. Critically the real confined attacker (the wrapped CMD) **can't reach this layer at all**: its stdout is redirected to stderr and stdin is nil, so it can't speak yamux — it's limited to TCP 127.0.0.1:3128, which only emits the fixed `proxy` target. Defense-in-depth nit: the host's name read is `bufio.ReadString('\n')` with **no size cap** (1 MiB buffered) — only reachable by a compromised inside bridge.

**X10 Resource exhaustion — no limits (limitation, low-medium).** 300 concurrent tunnel streams to a local sink all opened with no rejection; host bridge fds rose to 308 and it opened 300 upstream connections (`x10-bridge.log`). The proxy has **no connection cap and no idle timeout on established tunnels** (`io.Copy` to EOF; only a 15 s dial + 30 s header timeout); yamux has no stream-count limit (4 MiB window each). A confined CMD can open unbounded streams, each forcing a host→allowlisted-upstream connection — host DoS plus connection amplification toward allowlisted hosts.

## Five most serious findings
1. **X6 fronting bypass** — reach any origin co-fronted with an allowlisted host (github.com fetched 200 through api.github.com). The allowlist does not constrain the actual TLS destination. Medium-high.
2. **X7 host-filesystem exposure** — untrusted root in the sandbox reads all host container files incl. root-owned 0600, by default (`rootfs=/`). High as a latent property; the design's safety rests entirely on "no secrets in the container."
3. **X8 secret-via-env leak path** — `--env`/`RUN_ENV` values persist in data-plane logs and the non-disableable Admin Activity audit log. Medium; a foot-gun in the provided `crun.py`.
4. **X10 unbounded streams/connections + no proxy idle timeout** — host DoS and amplification to allowlisted hosts. Low-medium.
5. **D1/X4 + X9 robustness** — "every address is public" is false (allows if any is public; no private reach, but the guarantee is weaker than documented) and the host's stream-name read is unbounded. Low; correctness/defense-in-depth.

## Three changes that close the most risk for least work
1. **Make the proxy SNI-aware on CONNECT** (closes X6): peek the TLS ClientHello on the hijacked connection and reject if the SNI is not itself on the allowlist (and/or pin the dialled IP to the allowlisted name). A few lines; turns fronting from "works" to "blocked" for the common case.
2. **Set `--rootfs` to a minimal dedicated rootfs and run the sandboxed command as non-root** (closes X7): one flag plus a user, removing the default read of the entire host container; keep the rule that no secret is ever written to the host FS.
3. **Stop routing anything sensitive through `--env`/`RUN_ENV`** (mount secrets instead) and **add a per-execution stream/connection cap in `stdio-bridge` plus an idle timeout on established proxy tunnels** (closes the X8 leak path and the X10 DoS) — each a small, local change.

## Where the prompt was ambiguous, wrong, or made me guess (most valuable part)
- **"Do not change project-level IAM" conflicts with the target's own `setup.sh`**, which does `projects add-iam-policy-binding` for the build SA (logging.logWriter, storage.objectViewer). I skipped `setup.sh` and used a user-owned EU bucket + resource-level bindings + GCS logs to avoid project IAM, but the prompt should say whether running the target's documented setup counts as "changing project IAM."
- **Building in EU is non-obvious and undocumented by the target.** `gcloud builds submit` defaults to a **US** staging bucket (violates the EU org policy), and regional builds (`--region`) default to the **compute SA, which had zero roles**. I had to discover `--gcs-source-staging-dir`/`--gcs-log-dir` on a self-made bucket + resource-level grants. `run.sh`/`setup.sh`/`cloudbuild.yaml` as written would not build in this project; a tester should be warned.
- **X1/X2 "direct, ignoring the proxy" is contaminated by curl.** Inside the sandbox the launcher injects `http_proxy`, so `curl http://169.254.169.254/...` silently goes *through* the proxy (returns 403, not a network error). Only a tool that ignores env (raw socket / `probe dial`) is a valid "direct" test. The prompt should specify that.
- **Public DNS test names (sslip.io/nip.io) don't resolve from the test environment**, and `speed.cloudflare.com` (the 2nd allowlist entry) didn't resolve either. I used `/etc/hosts` + the Go resolver for X4/X5 and GitHub's edge for X6. The prompt assumes public DNS-based test names are usable; here they weren't, and the "both private+public" case can't be built with sslip.io anyway (one IP per name).
- **X8's real risk is the provided tooling, not just "the platform."** The prompt frames X8 as "does the platform log args/env," but the sharper issue is that `crun.py`'s `RUN_ENV` writes values into the audit log; worth pointing at the tool.
- **Whether extending the launcher for controls is allowed is unstated.** I judged it acceptable to add `EGRESS`/`PLANT` env knobs (leaving proxy/bridge and the `sandbox do` flags identical) because there was no other way to produce the X1 `--allow-egress` control and X7 mode-varied markers; the prompt could say so explicitly.
- **`crun.py apply` printed `200 {}`** (empty status) on first create, which is ambiguous about create-vs-update; minor.
